# 规则文件格式规范（rules-file-spec）

项目规则文件是 AI 与协作者在项目中的"行为契约"：记录**已经做出的决策和约定**，而不是记录代码事实。本文件定义规则文件的默认结构、条目句式和变更分类，供 rule-keeper-pro 在采集、评估、应用与校验阶段使用。

## 1. 文件与位置

- 默认文件：项目根的 `AGENTS.md`。
- 已有其他规则文件时优先复用：`CLAUDE.md`、`.cursor/rules/*.md`、`.github/copilot-instructions.md`、`docs/RULES.md` 等（由 `scripts/find_rules_files.py` 定位）。
- 同一项目只维护一个规则文件，避免多份规则互相矛盾。

## 2. 行数上限与 maxLines 覆盖

- 默认硬上限 **150 行**。
- 在文件头部声明可覆盖：`> maxLines: 200`（写在引用块元数据区）。
- 校验脚本（`validate_rules.py`）优先读取文件头部的 `maxLines` 声明，无声明时使用默认值 150。
- 超过上限时必须执行超额瘦身（见 SKILL.md Step 5），不得直接保存。

## 3. 文件结构模板（6 段）

```markdown
# <项目名> 项目规则

> 最后更新：YYYY-MM-DD
> maxLines: 150
> 适用范围：<本文件约束的范围，如"本仓库所有代码与 AI 协作流程">

## 1. 项目指纹
- **项目名**:
- **目标**(一句话):
- **技术栈**:
- **仓库**:

## 2. 架构骨架
**分层**(自上而下,依赖方向:上层依赖下层):
- Layer 0(底层/基础设施):一句话
- Layer 1:
- Layer 2:

**模块**:
- `module_a` —— 职责一句话
- `module_b` —— 职责一句话

**禁止**:
- 跨层调用

## 3. 硬约束
**DO**:
1. (祈使句,动词开头,可校验)
2. (祈使句,动词开头,可校验)

**DON'T**:
1. (祈使句 + 一行原因)
2. (祈使句 + 一行原因)

## 4. 关键决策
| 日期 | 决策 | 选择 | 原因 | 拒绝的替代 |
|---|---|---|---|---|
| YYYY-MM-DD | 例:持久化方案 | SQLite | 零运维 + 单文件 | Postgres(运维成本) |

## 5. 工作流
- **开发**:步骤
- **测试**:步骤
- **提交**:步骤
- **文档**:步骤

## 6. 元规则
- 总行数 ≤ 150(硬上限,超过必须瘦身;可在头部声明 maxLines 覆盖)
- 触发更新:功能完成 / PR 合并 / 会话收尾
- 更新协议:增量 Edit,不全量重写;镜像相邻条目格式
- 边界:用户偏好 → `USER.md`;历史活动 → memory 日志;项目设计 → 本文件
- 自检:每条都祈使句、都可校验、跨章节不重复

## 变更记录
- 2026-09-08：新增 <条目>（原因）
```

### 6 段行数预算

| § | 章节 | 用途 | 行数预算 |
|---|---|---|---|
| 1 | 项目指纹 | name / goal / stack / repo | ≤8 |
| 2 | 架构骨架 | 分层、模块、依赖方向 | ≤40 |
| 3 | 硬约束 | DO / DON'T 祈使句 | ≤50 |
| 4 | 关键决策 | 表格：决策 + 原因 + 拒绝的替代方案 | ≤30 |
| 5 | 工作流 | dev / test / commit / doc ritual | ≤20 |
| 6 | 元规则 | 本文件自身的更新协议 | ≤10 |

空分区删除；分区按需增减但不超过 6 段核心结构。

## 4. 条目句式

单条规则用一行（或两行：规则 + 原因），句式：

- `必须 / 禁止 / 优先 / 允许 + 动作 + 对象`，可选附 `（原因：...）`。
- 示例：
  - `禁止在服务端代码中拼接用户输入生成 SQL（原因：注入风险）`
  - `新增 API 必须配套 OpenAPI 文档并跑通契约测试（原因：保证前后端可独立联调）`

**质量标准（逐条自检）**：

- **可执行**：读的人知道具体该做什么 / 不做什么。
- **可验证**：能判断是否被遵守（最好可由 lint / CI 部分校验）。
- **具体**：不含"尽量""合理"等无法判定的词，除非有明确边界。
- **不写常识**：只写本项目特有的约定与决策，不写通用工程常识。
- **不写实现细节**：不写"某文件里有什么"，只写"必须 / 禁止做什么"。
- **祈使句**：每条 bullet 以动词开头（DO / DON'T / 必须 / 禁止 / 优先 / 允许）。

## 5. 分区与数量闸门

- 分区按需增减，空分区删除；每个分区 3–10 条为宜。
- 全文件条目总数建议 ≤ 60；超过时先合并 / 删除低价值条目，再新增。
- 一条规则只表达一个约束；多约束拆成多条，便于单独修订与删除。

## 6. 变更分类

| 分类 | 判定条件 |
| --- | --- |
| 新增 ADD | 既有规则未覆盖，且过三道闸门 |
| 修订 REVISE | 行为已变化，或原表述不准 / 误导 |
| 删除 REMOVE | 已被推翻、失效、与现状不符 |
| 合并 MERGE | 与既有条目语义重叠，可归并 |
| 不变 NOOP | 信号不足、重复、或属于实现细节 |

**三道闸门**（rule-keeper-pro 阶段 3 使用）：

1. **高信号**：是决策 / 约定 / 边界 / 坑 / 验收标准，而非实现细节或临时状态。
2. **无重复**：先检索既有条目，确认未覆盖；语义重叠走"合并"而非"新增"。
3. **无矛盾**：与既有条目不冲突；冲突时先修订旧条目。

## 7. 好规则与坏规则示例

**坏规则（不要写）**：

- `- 代码要写得清晰`（常识，不可验证）
- `- 使用 React 18`（技术栈清单是代码事实，不是行为约束——除非配套约束"不得引入其他 UI 框架"）
- `- 注意处理异常`（不具体）

**好规则（值得写）**：

- `- 新增对外接口必须返回统一错误码结构（原因：客户端只解析一种错误格式）`
- `- 禁止在迁移脚本中直接修改线上数据（原因：曾导致一次数据回滚事故）`

## 8. 防膨胀

- 能由工具自动保证的内容（lint、format、CI）不写进规则；只写"必须在 CI 里跑 lint"这类行为约束。
- 临时说明（一次性、短期会变的）不写。
- 每次更新都做一次"删除"检查：有没有可以被删掉的旧条目。
- 变更记录保留最近 20 条即可，更早的清理。
- 超过行数上限时：长说明改链接、同模式合并、删除"过去是什么"的条目；仍超则让用户选保留哪些。
