# rule-keeper-pro：项目规则持续维护

在每次迭代中保持项目规则文件与项目现状一致：把新决策、新约定、新边界和踩过的坑固化为规则，修订或删除已过期内容，防止规则漂移与膨胀。

## 核心原则

- **只写高信号规则**：决策、约定、边界、踩坑、验收标准；不写实现细节、临时状态、代码里已能体现的事实。
- **少而硬**：规则宁缺毋滥；能由 lint / CI 等工具自动保证的内容不写进规则。
- **每次变更过三道闸门**：高信号、无重复、无矛盾（判定标准见 references/rules-file-spec.md）。
- **无强信号就不更新**：评估后若没有值得固化的变更，如实报告"本轮无需更新"，不要为更新而更新。
- **薄而硬**：6 段固定结构，默认 150 行硬上限（可在文件头部声明 `maxLines` 覆盖），每段有行数预算，超额必须瘦身。

## 触发时机

以下三个时机**主动**触发：

1. **功能完成** —— 一个非平凡 feature 已落地（`feat: ...` commit 或 PR 可合并）。
2. **PR 合并** —— 团队已接受变更进入主干。
3. **会话收尾** —— 用户给出收工信号（"今天先到这"/"先这样"/"收工"/"merge 吧"等）。

**不要**在常规编辑、热修复、debug 过程中触发 —— 会产生噪音，稀释契约质量。

## 工作流程

### Step 1 — 定位规则文件

1. 确定项目根目录（用户给出的项目路径，否则为当前工作目录）。
2. 运行 `python3 scripts/find_rules_files.py <项目根>`，列出候选规则文件。
3. 优先复用已存在的规则文件（按项目实际约定；AGENTS.md 为默认首选）。
4. 若不存在规则文件且用户要求维护规则：从 `assets/AGENTS.md.tmpl` 拷贝模板到项目根，新建 `AGENTS.md`；用户明确指定其他位置 / 命名时按其指定。
5. 只读取和修改项目内的规则文件，不越界修改其他文件。

### Step 2 — 读取现状与采集变更信号

1. **通读规则文件全文**，记录当前行数、已填充的章节、`maxLines` 声明值（若有）。
2. 快速回顾本次变更（最近的 PR diff 或本次会话产出），从以下来源收集"可能值得写入规则"的信号：
   - **会话决策**：本轮确认的技术选型、架构决策、取舍理由（用户拍板或与用户达成一致的决定）。
   - **git 历史**（若是 git 仓库）：自上次规则更新以来的 `git log` / `git diff`，关注新增模块、重构、接口变化、反复出现的问题修复。
   - **约定与风格**：本轮新出现的命名 / 结构 / 流程约定，尤其是用户纠正过的写法。
   - **踩过的坑**：本轮发现并绕开的陷阱、易错点、禁忌操作。
   - **验收标准**：本轮确立的完成定义、测试或验证要求。
3. 对每个信号先做初筛：它是"决策 / 约定 / 边界 / 坑 / 验收标准"吗？是 → 进入 Step 3；否（实现细节、临时状态、常识）→ 丢弃。

### Step 3 — 评估并分类

逐条对照既有规则文件，为每个信号打分类标签：

| 分类 | 判定条件 |
| --- | --- |
| 新增 ADD | 既有规则未覆盖，且过三道闸门 |
| 修订 REVISE | 行为已变化，或原表述不准 / 误导 |
| 删除 REMOVE | 已被推翻、失效、与现状不符 |
| 合并 MERGE | 与既有条目语义重叠，可归并 |
| 不变 NOOP | 信号不足、重复、或属于实现细节 |

**三道闸门**（任一不满足即不写入）：

1. **高信号**：是决策 / 约定 / 边界 / 坑 / 验收标准，而非实现细节或临时状态。
2. **无重复**：先检索既有条目确认未覆盖；语义重叠走"合并"而非"新增"。
3. **无矛盾**：与既有条目不冲突；冲突时先修订旧条目，再决定是否新增。

同时按变化类型映射到 6 段结构中的目标章节：

| 变化类型 | 目标章节 |
| --- | --- |
| 仓库 / 栈 / 目标变更 | §1 项目指纹 |
| 新模块 / 新分层 / 新边界 | §2 架构骨架 |
| 新增硬性 DO 或 DON'T | §3 硬约束 |
| 新技术选型 / 推翻旧选型 | §4 关键决策 |
| 新增开发 / 测试 / 提交 ritual | §5 工作流 |
| 本文件自身更新协议变更 | §6 元规则 |

格式、条目句式和数量闸门见 references/rules-file-spec.md。

### Step 4 — 最小化写入

1. 先完整读取规则文件再动手。
2. 用 `Edit` 而不是 `Write`，保留原有措辞，只改该改的。
3. 严格按 references/rules-file-spec.md 的 6 段结构与条目句式修改；新条目**镜像相邻条目的格式**，不允许风格漂移。
4. 新增 / 修订条目尽量附一句"原因"，让未来的 AI 与人都能理解。
5. 若规范启用"变更记录"区，在文件尾追加一行：`- YYYY-MM-DD：新增 / 修订 / 删除 <条目>（原因）`。
6. 每次 Edit 后重新统计行数。
7. 只更新规则文件本身，不顺手修改代码或其他文档。

### Step 5 — 超额瘦身

若总行数超过上限（默认 150，或文件头部声明的 `maxLines` 值）：

1. 任何超过一行的说明 → 改成"详见 `<doc_path>`"，**绝不**在规则文件里塞长文。
2. 同模式多条 bullet → 合并为一条编号规则。
3. 描述"过去是什么"的条目 → 删除（rules 只描述当前状态）。
4. 仍超 → 把冲突抛给用户，让用户选保留哪些、砍掉哪些。

### Step 6 — 校验与自检

1. 运行 `python3 scripts/validate_rules.py <规则文件>`：必须无 [错误]；[警告] 逐条判断是否处理。
2. **自检清单**（保存前必跑，任何一项 = 否，立即修复再保存）：
   - [ ] 总行数 ≤ 上限（默认 150 或声明的 maxLines）
   - [ ] 每条 bullet 都是祈使句（动词开头）
   - [ ] 每条都可被 reviewer 校验
   - [ ] 跨章节无重复
   - [ ] §4 关键决策解释了**为什么**，不只**是什么**
   - [ ] 无任何"暂未决定 / 待讨论 / TODO 无 owner"等悬空项
3. 重读更新后的文件并主动找反证：新条目是否与旧条目矛盾？是否重复？是否仍属高信号？条数是否超闸门？

### Step 7 — 汇报

向用户交付：

- 规则文件路径；
- 变更小结：新增 n 条 / 修订 n 条 / 删除 n 条 / 合并 n 条，及各自原因；
- 当前行数 / 上限；
- 若判定"无需更新"，说明判定依据。

一句话格式：`<规则文件> updated: §X 新增 Y, §Z 改写 W. 当前 N 行 / 上限 M 行。`

## AGENTS.md 结构规范（6 段，默认 ≤ 150 行）

| § | 章节 | 用途 | 行数预算 |
| --- | --- | --- | --- |
| 1 | 项目指纹 | name / goal / stack / repo | ≤8 |
| 2 | 架构骨架 | 分层、模块、依赖方向 | ≤40 |
| 3 | 硬约束 | DO / DON'T 祈使句 | ≤50 |
| 4 | 关键决策 | 表格：决策 + 原因 + 拒绝的替代方案 | ≤30 |
| 5 | 工作流 | dev / test / commit / doc ritual | ≤20 |
| 6 | 元规则 | 本文件自身的更新协议 | ≤10 |

- 默认硬上限 150 行；在文件头部声明 `maxLines: 200` 可覆盖，适用于大项目。
- 完整模板见 `assets/AGENTS.md.tmpl`。

## 与其他文件的边界

| 文件 | 放什么 |
| --- | --- |
| `AGENTS.md`（本 skill 输出） | 项目设计 —— 代码**是**什么 / **必须**怎么写 |
| `USER.md` | 用户偏好 —— 语气、语言、工作风格 |
| `~/.workbuddy/MEMORY.md` 与 daily log | 历史 —— 做过什么、什么时候做 |

**绝不**把用户偏好写进 AGENTS.md。**绝不**把架构规则写进 USER.md。**绝不**把时间线活动写进 AGENTS.md。

## Anti-patterns（看到就改）

- 把完整文件树塞进 §2 —— 太长，用 1 行 + 链接代替。
- 写"我们正在考虑 X" —— rules 只描述当前状态。
- 链接外部文档却不写**取它的什么** —— reviewer 找不到点。
- 加 §7"未来想法" —— 出 scope，直接删。
- §3 里出现"沟通风格 / 语言偏好" —— 挪去 USER.md。
- 变更记录无限增长 —— 保留最近 20 条，更早的清理。
